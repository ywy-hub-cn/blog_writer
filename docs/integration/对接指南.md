# Blog-Writer 对接指南

> 本文档包含接口说明、完整调用示例、错误码、Webhook验证，开发对接看这一份就够了。
> 机器可读的完整接口定义见同目录 `openapi.json`，或运行中访问 `/docs`（Swagger UI）。
> 最后更新：2026-08-26

---

## 一、基础信息

| 项 | 值 |
|----|-----|
| Base URL | `http://服务器IP:8000`（Nginx反代后用域名） |
| 请求格式 | `application/json`（文件上传用 `multipart/form-data`） |
| 响应格式 | `{code, message, data, timestamp}` |
| 字段命名 | 默认 `snake_case`；Java对接设 `.env` 中 `RESPONSE_CASE=camel` 自动转驼峰 |
| 字符编码 | UTF-8 |

**统一响应示例**：
```json
{
  "code": 0,
  "message": "success",
  "data": { "task_id": "task_20260817_120000_abc123" },
  "timestamp": "2026-08-17T12:00:00"
}
```

## 二、鉴权

### 免登录接口（直接调用）
品牌管理、任务启动/查询/控制/日志/文件下载。生产环境建议配置 `BLOG_WRITER_TASK_AUTH=required` 强制鉴权；开发环境默认 `optional` 可匿名。

环境变量 `BLOG_WRITER_TASK_AUTH`：`required`（必填 Token/登录）或 `optional`（匿名 operator）。

可选增强：`.env` 设 `BLOG_WRITER_API_TOKEN=your-token`，则上述接口需加请求头：
```
X-API-Key: your-token
```

### 需登录接口（管理员）
节点CRUD、系统配置、统计信息，需先登录拿token，请求头加：
```
Authorization: Bearer <token>
```

**登录**：
```bash
curl -X POST http://localhost:8000/api/auth/login \
  -H "Content-Type: application/json" \
  -d '{"password": "admin123"}'
```
响应：
```json
{
  "code": 0,
  "data": {
    "token": "eyJhbGciOi...",
    "role": "admin",
    "expires_in": 86400
  }
}
```

其他鉴权接口：`POST /api/auth/logout`、`GET /api/auth/verify`、`POST /api/auth/change-password`。

## 三、完整对接流程

### 步骤1：上传品牌资料

```bash
curl -X POST http://localhost:8000/api/brands/upload \
  -F "display_name=SMS Boosting" \
  -F "files=@品牌知识库.md" \
  -F "files=@语气调性指南.md"
```
响应：
```json
{
  "code": 0,
  "data": {
    "brand_id": "sms-boosting",
    "display_name": "SMS Boosting",
    "file_count": 2
  }
}
```

> `brand_id` 由中文显示名自动转拼音生成，后续启动任务用 `brands/<brand_id>` 作为 `brandPath`。

### 步骤2：启动写作任务

```bash
curl -X POST http://localhost:8000/api/tasks/start \
  -H "Content-Type: application/json" \
  -d '{
    "brandPath": "brands/sms-boosting",
    "keywords": "SMS API integration guide",
    "mode": "auto",
    "priority": 2,
    "userNote": "面向企业开发者，侧重集成步骤",
    "callbackUrl": "https://your-platform.com/webhook/blog-writer",
    "callbackSecret": "your-webhook-secret"
  }'
```

**请求字段说明**：

| 字段 | 必填 | 类型 | 说明 |
|------|------|------|------|
| `brandPath` | ✅ | string | 品牌资料路径，如 `brands/sms-boosting` |
| `keywords` | ✅ | string | 文章关键词，≤500字符 |
| `mode` | - | string | `auto`(默认) / `supervised` / `manual` |
| `priority` | - | int | 1低 / 2中(默认) / 3高 |
| `userNote` | - | string | 附加写作要求（无字数硬限制；前端启动前会确认字数） |
| `brandSiteUrl` | - | string | 品牌官网URL（可选；不传时 S000 会尝试从品牌知识库提取。用于内链校验与媒体库封面匹配） |
| `callbackUrl` | - | string | 任务回调地址 |
| `callbackSecret` | - | string | Webhook签名密钥 |
| `callbackEvents` | - | string[] | 订阅的事件列表（默认含终态 + `task.step_completed`） |
| `temperature` | - | float | 0-2，LLM温度 |
| `maxTokens` | - | int | 单步最大输出token |

响应：
```json
{
  "code": 0,
  "data": {
    "task_id": "task_20260817_120000_abc123",
    "status": "queued",
    "message": "任务已加入队列"
  }
}
```

**幂等启动（推荐 Java 编排使用）**：请求头 `Idempotency-Key: your-order-id`，服务端映射为稳定 `task_id`；重复请求返回 `idempotent_hit: true`。

```bash
curl -X POST http://localhost:8000/api/tasks/start \
  -H "Content-Type: application/json" \
  -H "Idempotency-Key: order-20260826-001" \
  -d '{"brandPath":"brands/sms-boosting","keywords":"SMS OTP guide"}'
```

**批量启动**：

```bash
curl -X POST http://localhost:8000/api/tasks/batch \
  -H "Content-Type: application/json" \
  -d '{
    "brandPath": "brands/sms-boosting",
    "tasks": [
      {"keywords": "SMS OTP guide"},
      {"keywords": "SMS API pricing"}
    ],
    "callbackUrl": "https://your-platform.com/webhook/blog-writer"
  }'
```

**任务状态枚举**：

| 状态 | 说明 | 终态 |
|------|------|------|
| `queued` | 排队中（并发满时等待） | - |
| `running` | 执行中 | - |
| `waiting_review` | 等待人工审核（supervised/manual模式） | - |
| `paused` | 已暂停 | - |
| `completed` | 成功完成 | ✅ |
| `failed` | 执行失败 | ✅ |
| `cancelled` | 已取消 | ✅ |

> `token_usage` 是任务累计消耗（取所有步骤中最大值，非求和）。

## 四、Webhook 回调

配置 `callbackUrl` 后，按 `callbackEvents` 订阅推送（默认包含终态与 `task.step_completed`）。

**默认可订阅事件**：

| 事件 | 说明 |
|------|------|
| `task.created` | 任务已创建 |
| `task.step_completed` | 单步完成 |
| `task.waiting_review` | 等待人工审核 |
| `task.completed` | 成功完成 |
| `task.completed_partial` | 部分完成 |
| `task.failed` | 失败 |
| `task.cancelled` | 已取消 |
| `task.rejected` | 审核拒绝 |

### 回调请求

```
POST https://your-platform.com/webhook/blog-writer
Content-Type: application/json
X-Signature: sha256=<hex_digest>
```

请求体（扁平结构，`event` + `task_id` 与业务字段同级）：
```json
{
  "event": "task.completed",
  "task_id": "task_20260817_120000_abc123",
  "timestamp": 1756089600,
  "status": "completed",
  "token_usage": 8766183,
  "keywords": "SMS API integration guide",
  "output_files": ["004 正文.md", "007 发布包.json"],
  "post_id": 123,
  "post_url": "https://your-site.com/blog/sms-api",
  "images_ready": true,
  "error": null
}
```

### 签名验证（必做，防伪造）

签名 = `HMAC-SHA256(请求体原始字节, callbackSecret)`，结果转十六进制小写，与 `X-Signature` 头的 `sha256=` 后部分比对。

**Python 示例**：
```python
import hmac, hashlib

def verify_signature(body: bytes, secret: str, signature_header: str) -> bool:
    expected = hmac.new(secret.encode(), body, hashlib.sha256).hexdigest()
    provided = signature_header.removeprefix("sha256=")
    return hmac.compare_digest(expected, provided)
```

**Java 示例**：
```java
import javax.crypto.Mac;
import javax.crypto.spec.SecretKeySpec;
import java.nio.charset.StandardCharsets;
import java.util.HexFormat;

public boolean verify(String body, String secret, String signatureHeader) throws Exception {
    Mac mac = Mac.getInstance("HmacSHA256");
    mac.init(new SecretKeySpec(secret.getBytes(StandardCharsets.UTF_8), "HmacSHA256"));
    String expected = HexFormat.of().formatHex(mac.doFinal(body.getBytes(StandardCharsets.UTF_8)));
    String provided = signatureHeader.substring("sha256=".length());
    return expected.equalsIgnoreCase(provided);
}
```

**Node.js 示例**：
```javascript
const crypto = require('crypto');

function verifySignature(body, secret, signatureHeader) {
  const expected = crypto.createHmac('sha256', secret).update(body).digest('hex');
  const provided = signatureHeader.slice('sha256='.length);
  return crypto.timingSafeEqual(Buffer.from(expected), Buffer.from(provided));
}
```

> 建议：验签失败直接返回403，不处理回调。回调需幂等（同一task_id可能重试）。

## 六、人工审核接口

supervised/manual模式下任务会进入 `waiting_review` 状态。

| 方法 | 路径 | 说明 |
|------|------|------|
| GET | `/api/tasks/reviews/pending` | 待审核列表 |
| POST | `/api/tasks/{id}/review` | 提交审核决策 |

**提交审核**：
```bash
curl -X POST http://localhost:8000/api/tasks/task_xxx/review \
  -H "Content-Type: application/json" \
  -d '{"decision": "approve", "modifications": {}}'
```

`decision` 取值：
- `approve` — 通过，继续执行
- `reject` — 驳回，退回上一步重新生成
- `modify` — 修改后通过，需传 `modifications`

## 十、错误码大全

| code | 含义 | 常见原因 | 处理建议 |
|------|------|----------|----------|
| 0 | 成功 | - | - |
| 1001 | 参数验证失败 | 字段缺失/类型错误/关键词超长 | 检查请求体字段和类型 |
| 1002 | 认证失败 | 密码错误/token无效/过期 | 重新登录或检查X-API-Key |
| 1003 | 权限不足 | 普通用户调管理接口 | 用管理员token登录 |
| 1004 | 资源不存在 | task_id/brand_id/node_id错误 | 检查ID是否正确 |
| 1005 | 状态不允许 | 对已完成任务调pause等 | 检查任务当前状态 |
| 1006 | 品牌不存在 | brandPath指向的品牌未上传 | 先上传品牌资料 |
| 1007 | 文件问题 | 文件过大/格式不支持 | 单文件≤10MB，仅.md/.txt |
| 1008 | 并发已满 | 同时运行任务达上限 | 等待或调大MAX_CONCURRENT_TASKS |
| 5000 | 服务器内部错误 | LLM调用失败/代码异常 | 查看任务日志 `/api/tasks/{id}/logs` |

**错误响应示例**：
```json
{

  "message": "参数验证失败",
  "data": {
    "details": ["brandPath: Field required", "keywords: 不能为空"]
```

## 十一、WordPress 发布说明

任务最后一步（S011）会发布到 WordPress 草稿，并上传正文本地图片替换为媒体库 URL。

- **已配置** `brands/<brand_id>/wp-config.json`：真实创建 draft，`images_ready=true` 才算成功
- **未配置**：默认 hard fail，不再自动 dry-run 伪造成功；仅开发联调可显式传 `--dry-run`（`post_id=0`）

**配置文件**：`brands/<brand_id>/wp-config.json`
```json
{
  "site_url": "https://blog.yourcompany.com",
  "username": "editor",
  "app_password": "xxxx xxxx xxxx xxxx xxxx xxxx"
}
```

- `app_password` 是WP后台→用户→个人资料→应用密码 生成的，**不是登录密码**
- 发布状态固定为 `draft`（草稿），不会直接上线
- 自动设置特色图像、写入Rank Math SEO标题/描述
- 需要WP 5.6+且REST API启用

## 十二、常见问题排查

**Q: 启动任务返回1006品牌不存在？**
A: `brandPath` 要写 `brands/<brand_id>`，brand_id是拼音（如`sms-boosting`），不是中文显示名。先调 `GET /api/brands` 确认。

**Q: 任务一直queued不开始？**
A: 并发满了。调 `GET /api/tasks/concurrency` 看available，或调大 `.env` 中 `MAX_CONCURRENT_TASKS`（默认5）。

**Q: 任务failed了怎么看原因？**
A: 调 `GET /api/tasks/{id}/logs` 看最后几十行日志，常见是LLM API超时/密钥错/品牌文件缺失。

**Q: token_usage数字很大正常吗？**
A: 单篇文章约500万-1500万Token（含多步重试），是累计值不是单步值。费用按 ¥2/百万Token 估算。

**Q: Webhook没收到回调？**
A: 检查 callbackUrl 是否公网可访问、出站是否放行、接口是否返回 2xx。默认订阅终态与 `task.step_completed`；若只配了部分 `callbackEvents`，中间步骤不会推送。验签请用 **HTTP body 原文**，不是拼接字符串。

**Q: 幂等键和 task_id 关系？**
A: 请求头 `Idempotency-Key` 会映射为 `task_<key>` 形式的 `task_id`；重复 POST 返回同一任务且 `idempotent_hit: true`。

**Q: 下载文件404？**
A: 文件名含中文/空格需URL编码；或任务还没生成该文件（看results中的output_files）。

**Q: supervised模式任务卡住？**
A: 进入waiting_review状态等人工审核，调 `GET /api/tasks/reviews/pending` 查看，提交 `POST /api/tasks/{id}/review` 决策。

**Q: 响应字段是驼峰还是下划线？**
A: 默认snake_case。Java对接在 `.env` 设 `RESPONSE_CASE=camel`，所有响应自动转驼峰，请求体两种都接受。
